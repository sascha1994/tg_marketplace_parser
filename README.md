# Telegram Marketplace Parser

Docker-образ собирается в GitHub Actions и публикуется в GitHub Container Registry (GHCR). Сервер не собирает образ и не обновляется автоматически: чтобы установить новую версию, на сервере нужно скачать выбранный образ из GHCR и перезапустить сервис через Docker Compose.

## Релизные ветки и версии образов

В `main` ведётся основная разработка. Каждый push в `main` запускает тесты и после их успешного прохождения публикует:

- `ghcr.io/sascha1994/tg_marketplace_parser:latest`
- `ghcr.io/sascha1994/tg_marketplace_parser:sha-<commit>`

Для релиза создайте ветку от коммита, который нужно выпустить, и отправьте её в формате `release/x.y.z`, например:

```bash
git switch main
git pull
git switch -c release/1.4.0
git push -u origin release/1.4.0
```

Для этой ветки GitHub Actions запустит тесты и, если они пройдут, опубликует образы `:1.4.0` и `:sha-<commit>`. Допускается и имя `release/v1.4.0`, но тег образа всё равно будет `:1.4.0`. Последующие push в ту же релизную ветку обновляют эти теги. Не используйте один номер версии для разных релизов.

Исправления конкретного релиза отправляйте в его релизную ветку и дождитесь успешной публикации перед обновлением сервера. Не забудьте перенести необходимые исправления обратно в `main` — например, через merge или cherry-pick. Pull request в `main` или `release/**` запускает тесты, но не публикует образ.

Пакет GHCR должен быть публичным, чтобы сервер мог скачать образ без учётных данных. Для приватного репозитория или пакета настройте на сервере вход в GHCR с GitHub-токеном, у которого есть право `read:packages`.

## Развёртывание на сервере

Инструкция рассчитана на Linux-сервер с установленными Docker Engine и Docker Compose plugin.

1. Создайте на сервере каталог, например `/opt/tg_parser`, и скопируйте туда `docker-compose.yml`.
2. Создайте `/opt/tg_parser/.env` с параметрами приложения. Файл храните только на сервере, не добавляйте его в Git. В этот же файл добавьте `PARSER_IMAGE_TAG=latest` для сборок из `main` или `PARSER_IMAGE_TAG=1.4.0` для релиза. Compose использует `.env` для выбора образа и передаёт значения контейнеру.
3. Убедитесь, что данные контейнера сохраняются на постоянном диске. По умолчанию Compose использует `/opt/tg_parser/data`. Чтобы выбрать другой каталог, добавьте в `/opt/tg_parser/.env` строку `PARSER_DATA_DIR=/absolute/path/to/data`.
4. После успешного завершения соответствующего GitHub Actions workflow обновите контейнер:

```bash
cd /opt/tg_parser
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100
```

`docker compose pull` загружает выбранный образ из GHCR, а `docker compose up -d` пересоздаёт контейнер, если образ изменился. На сервере не нужны исходный код проекта или инструменты сборки. Для обновления `latest` повторяйте команды, когда захотите установить новую сборку. Для релиза сначала измените `PARSER_IMAGE_TAG` на новый номер версии, затем выполните команды.

Dockerfile хранит Python-зависимости, системные библиотеки Chromium, сам браузер и код приложения в отдельных слоях. Поэтому изменения только в коде не требуют повторно скачивать большой браузерный слой. После изменения структуры слоёв первая установка новой сборки может скачать их заново; последующие обновления смогут переиспользовать неизменившиеся слои.

### Первый запуск и перенос существующего сервера

Перед первым запуском подготовьте `.env` приложения и каталог данных. При переносе с существующего сервера остановите старый контейнер и задайте `PARSER_DATA_DIR` равным пути к прежнему каталогу данных. Не удаляйте базу, сессии и другие данные приложения; перед обновлением сделайте резервную копию.

## Откат

Для отката укажите в `.env` прежний номер релиза или тег коммита `sha-<полный-SHA-коммита>`, затем выполните:

```bash
docker compose pull
docker compose up -d
```

Проверьте журнал командой `docker compose logs`. Чтобы вернуться к обновлениям из `main`, установите `PARSER_IMAGE_TAG=latest`.
